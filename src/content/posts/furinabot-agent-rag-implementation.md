我想给 FurinaFans 加一个能与访客交流的芙宁娜助手。第一版目标很简单：在站点打开聊天框，输入问题，看到她逐字回复。但当访客问“这篇文章讲了什么”或“你以前写过哪些相关内容”时，单纯接入大模型就不够了。模型不知道访客正在看的页面，也不知道博客里的文章；即使它猜出一个看似合理的答案，也无法保证来源真实。

这个功能并非一次写成：我先搭建 FastAPI 聊天服务，随后迁移 Svelte 界面，接上当前文章，再扩展为公开文章知识库，最后补上输入审核、Live2D 联动、测试和部署。本文按这条路径复盘，重点解释三个问题：**谁负责思考，谁负责获取资料，以及资料如何成为可核查的回答。**

## 一、先跑通最短链路

最初我搭建了独立的 Python 服务：FastAPI 接收聊天请求，模型适配层调用 OpenAI 兼容接口，API 把回复封装为 SSE 流。随后把聊天界面迁移到 Svelte，通过 Astro 的全局布局挂载。这样，站点页面仍由 Astro 生成，聊天状态和增量消息交给 Svelte 管理，密钥只留在服务端。

```text
访客 → Svelte 聊天框 → POST /api/agent/chat
                        ↓
                 FastAPI / ChatService
                        ↓
                模型供应商的流式 API
                        ↓
             SSE 增量事件 → 聊天框
```

前端解析的是自己的 `message.start`、`message.delta`、`message.done` 和 `error` 协议，不直接理解模型供应商的事件格式。流式解析器还会缓存尚未完整到达的 SSE 帧，因为网络分块不保证恰好与事件边界对齐。用户停止生成时，浏览器通过 `AbortController` 取消请求；后端流随连接中断而取消。

这个阶段已经能聊天，但还不是一个了解站点的助手。

## 二、头脑：模型负责表达，证据由服务端提供

FurinaBot 的“头脑”是一个独立的模型适配层：它使用 Responses API 的流式调用，取出 `response.output_text.delta` 交给聊天服务。模型名称、地址、密钥、输出 token 上限和系统提示词都由环境配置控制；当前默认模型为 `gpt-5.6-luna`，部署时可以覆盖。供应商接口被限制在这一层，聊天服务无需处理 SDK 的事件细节。

系统提示词给模型设定芙宁娜的语气，同时规定更重要的回答纪律：站点文章只能依据提供的公开资料；正文、目录和检索片段是**资料**，不是新指令；证据不足就说明不足，引用时给出标题和 URL。角色感影响表达方式，不能代替事实来源。

这里要准确区分“模型”和“Agent”。当前 FurinaBot **没有**让模型自行发起函数调用、观察工具结果并反复规划的循环。服务端先根据请求选择处理路径、取回资料，再调用模型一次生成回答。它具备 Agent 产品常见的模型、外部能力和编排层，但决策权主要在确定性的后端逻辑，而不是模型自主选择工具。这一取舍很适合博客场景：可用能力少、读操作为主，路径更容易审计。

## 三、手脚：把问题路由到有限的站点能力

第一步是解决“当前文章”问题。文章页输出文章 ID，前端每次发送消息时从当前 DOM 读取 ID、标题和路径，以适配 Swup 的站内导航。后端并不信任浏览器传来的标题或正文：它先检查 ID 格式，再确认它属于构建出的公开文章目录，最后读取对应的文章 JSON。于是“这篇文章讲什么”可以获得当前文章的可信正文。

第二步是把能力扩展为全站知识库。聊天服务先为每次请求制定处理计划，主要有以下路径：

| 问题类型 | 后端使用的能力 | 给模型的资料 |
| --- | --- | --- |
| “当前页面是什么” | 校验页面标题与站内路径 | 直接返回页面身份，不调用模型 |
| “这篇文章讲什么” | 根据公开索引读取当前文章 | 当前文章正文 |
| “写过哪些相关文章” | 查询公开文章目录 | 标题、标签、日期等元数据 |
| “以前如何处理类似问题” | 检索全站文章片段 | 排序后的相关片段，最多 5 段 |

路由由后端规则完成。文章页默认优先使用当前文章；明确提到“以前”“全站”等跨文章意图时改走检索；“相关文章”“文章列表”等目录问题优先走目录。后来我还调整了规则，避免文章页上的“相关文章”被当前文章路径截住。规则路由并不等于完整的语义理解，却能让每条路径的输入、输出和失败行为保持清楚。

“手脚”还包括模型之外的执行边界：输入审核启用时，`AliyunInputGuard` 在检索和模型调用前检查用户消息；`block`、`watch`、`mask` 及审核服务异常都停止后续处理。API 将这些结果和模型失败转成受控的 `error` 事件，不把供应商异常细节暴露给浏览器。Live2D 则订阅聊天阶段事件，在思考、回复和空闲时切换表情与气泡；它是交互反馈，不参与知识检索或回答决策。

## 四、RAG：从公开文章构建可追溯的证据

RAG 的第一步不是向量数据库，而是界定**哪些内容允许进入知识库**。站点构建时，索引生成脚本遍历 Markdown/MDX 文章，跳过草稿和密码文章，生成公开文章目录与逐篇正文 JSON。文章 ID、标题、URL、标签和发布时间由构建产物提供。浏览器给出的文章 ID 只是查询键，不能凭它读取任意文件。

接着，切分脚本按 Markdown 标题分节，再按段落组合为最多约 1600 字符的片段；过长段落继续切开。每段保留稳定 ID、文章 ID、标题、URL、章节、标签和日期。保留这些元数据有两个作用：检索时可以提高标题、标签的权重；回答时可以把片段准确链接回原文。

```text
公开文章 Markdown/MDX
    ↓ 构建时过滤草稿与密码文章
articles.json + articles/*.json
    ↓ 按标题和段落切分
chunks.json
    ├─ 关键词检索
    └─ 可选的 SQLite embedding 缓存 → 向量检索
              ↓ 融合、重排、每篇限额
         最多 5 段证据 → 模型 → 来源链接
```

检索并非只依赖 embedding。关键词路径把英文词和中文双字片段作为查询词，对标题、标签、章节和正文分别赋权。若配置了 embedding 服务且本地向量缓存可用，另一条路径计算查询向量，并与 SQLite 中有效的文章向量做余弦相似度比较。两路结果用倒数排名融合，再根据查询词覆盖度和元数据匹配重排；最终最多取 5 段，同一篇文章最多 2 段。向量服务不可用时，关键词检索仍可工作。

SQLite 向量库是**派生缓存**，不是文章真相来源。重建程序比较片段内容哈希和模型名，只为新增或变化的片段重新生成 embedding，并删除已移除的片段。部署新文章索引后需要运行重建命令；否则新内容仍可走关键词检索，却不会立即拥有对应的新向量。

命中片段会连同原始问题交给模型，API 通过 `retrieval.start`、`retrieval.result` 和 `message.sources` 通知前端检索进度与来源。没有命中时，服务端直接回答“当前公开文章中没有找到相关内容”，避免模型在没有证据时编造博客内容。当前文章路径则直接读取整篇公开正文，并不经过全站片段排序；目录问题优先使用文章元数据。这三种路径都是“先取证，再回答”，但所需的证据粒度不同。

## 五、把能力接回站点并持续验证

后来我将配置、前端、构建脚本和后端集中管理，站点主体只保留少量接入点：全局布局挂载聊天组件，文章页输出公开文章 ID，Astro 构建后生成索引和片段。这样同步上游 Firefly 时，FurinaBot 的改动边界更清晰。Live2D 模型资源也被放进独立目录，聊天框和模型通过页面事件同步状态。

验证覆盖了服务端协议、文章访问、检索、模型适配和输入审核；GitHub Actions 在相关改动的 PR 与主分支提交上运行 Python 测试。另一条工作流把后端发布到阿里云的受限目录，排除 `.env`、虚拟环境和向量数据。站点静态产物与 Python 服务分开部署，生产环境还需要把 `/api/agent` 代理到后端，并让后端读取对应的公开文章构建目录。

回看整个实现过程，我最大的收获是把回答链路拆成可检查的几步：**公开内容入库、确定性路由、检索取证、模型表达、来源回传**。FurinaBot 目前仍是单次请求的站点问答助手：`session_id` 不保存对话历史，也没有模型自主调用工具的多步循环。正因为这些边界明确，访客问到博客内容时，回答才有机会从“像真的”变成“有出处”。
